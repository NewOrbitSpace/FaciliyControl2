# Turbomolecular-pump protection software review — 2026-11-27

The review found reproducible protection failures. In particular, a Manual gate-open confirmation can open onto atmosphere after the pressure changes while the dialog is pending; missing/invalid speed can be treated as stopped. Existing successful operation does not exercise those cases.

Scope: shared Python facility-control implementation at git `9633340bb8be8b407e02933d4101d2fa5d7748dd`, the two active YAML profiles, configuration/DAQ/serial interfaces, existing tests and repository I/O descriptions. Legacy LabVIEW descriptions were used as historical context, not independently validated. The pre-existing untracked `thrust_balance_control/` was left untouched and is outside this pump-control review. Production control code and protection settings were not changed. Added tests, evidence and proposed fixes only. User subsequently confirmed hardware identities are unavailable and requested emphasis on software bugs and avoiding atmospheric exposure of a fast rotor.

No exact equipment manuals or authoritative as-built wiring/P&ID were present in the repository. Manufacturer-document searches cannot establish installed applicability without identities. No controller-native protection is credited as verified. Code reads fault/warning/status parameters and retries communication; that does not prove which temperature, overload, run-up, venting or power-loss protection the installed drive enables. Establish these from matching manuals and a read-only parameter record before allocating protection to them. Software currently owns sequencing, pressure/exposure decisions, external valve/backing/chiller commands, gauge heuristics and communication alarms.

Additionally, chiller run feedback is not proof of cooling flow; displayed temperatures have no software validity/trip model; valve feedback cannot represent both-open-and-closed contradictions; no measured vent-rate protection is implemented. These are unresolved allocation/specification hazards, not invented limits to insert into software.

**F11, P1 — continuous protection depends on mode.** `controller.py:980` explicitly logs a rapid rotor-speed drop with “No automatic action” in Manual/Admin and continues. `_decide_manual_or_admin` (`controller.py:1258`) checks requested actions but does not run the Auto pressure/exposure fault response. Manual interlocks therefore do not provide continuous protection after an initially permitted configuration becomes hazardous. The existing `test_turbo_speed_drop.py` deliberately tests this warning-only policy. Proposed fix: place mandatory continuous protective functions outside the operating-mode state machine, with approved fault responses that also apply to Manual/Admin. This is a code-confirmed policy gap; hardware protection must not be assumed to cover it.

Timing review also found the controller's default deadline clock is `time.time` (`controller.py:145`), whereas the outer loop and serial worker use monotonic time. Wall-clock correction can change holds/debounce/sequence intervals. Separate scheduled civil-time starts from monotonic elapsed-time protection timers, and verify forward/backward clock adjustments. That scenario was not executed in this review.

Do not infer a 100 ms protection response from `loop_period_ms: 100`: the small profile requests 200 samples at 1000 Hz for its finite gauge acquisition (200 ms of sampling alone), and the NI backend performs other reads sequentially with their own waits/timeouts (`hal/nidaqmx_backend.py:310`). Establish the actual acquisition and reaction budget, including sample age and filtering, on the isolated commissioning arrangement. Real acquisition timing was not measured here.

**F12, P2 — link validation can divide by zero.** `drivers/pfeiffer_pv.py:722` formats `pings / dt` without checking whether two `time.monotonic()` observations differ. Both `test_validation_passes_on_a_healthy_rs485_pump` and `test_validation_flags_remote_priority_and_wrong_address` reproduced `ZeroDivisionError` on the in-memory bus in this environment. Proposed fix: use an appropriate high-resolution elapsed clock and explicitly handle nonpositive elapsed duration with an unavailable rate; continue reporting actual replies/errors. A higher-resolution clock alone is not a substitute for guarding division. This is a diagnostic-path defect, not proof of a pump-control failure on hardware.

## Verification limits

Completed existing-test batches also recorded 29 failures (see `results.md` and retained XML), including alarm, compressor, shutdown and gate-sequence expectations. Aside from the identified F12 diagnostic crash, their individual causes remain unresolved. They are a verification blocker, not evidence to label every failure a production bug or to dismiss every failure as test timing. The broad run was stopped in excessive legacy startup retries; it was not a full-suite pass.

Tests exercise simulated physics or Python authorization, not pump survival. Existing test oracles share configuration thresholds with the implementation, so they cannot validate manufacturer limits. The fault campaign explicitly tolerates certain pressure excursions/air braking/power/cooling failures in `tests/safety_scenarios.py:306–335`; `SAFETY_STRICT=1` does not disable its UNAVOIDABLE filter. Such events remain unresolved plant hazards even when tests pass.

No measured temperature/flow or vent-rate model; no validation of stuck-closed versus leaking valves, dual contradictory endpoint contacts, calibration drift, OS scheduling bounds, electrical polarity, independent watchdog, physical retained outputs or real process power-cycle. Generated tests are bounded and seeded, not exhaustive. New restart tests enumerate states but do not emulate every reachable substate, persistent serial drive state or NI power cycle. No claim that every prohibited transition or concurrency interleaving has been verified.

Reference approach: requirements, implementation review, traceable verification and discrepancy handling follow the lifecycle themes described by [IEC's official IEC 61508-3:2010 scope](https://webstore.iec.ch/en/publication/5517). This report is not a standards compliance or certification assessment. Passing tests or high coverage cannot establish safety.
